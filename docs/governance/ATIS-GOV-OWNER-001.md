# ATIS-GOV-OWNER-001 — Owner Governance and Delivery Discipline

Status: PROPOSED — pending owner acceptance and protected merge
Governing method: Smoothflow V5.5
Scope: ATIS engineering assistance, Codex tasks and publication decisions
Effective for this proposal: 2026-10-21

## 1. Precedence and change control
The latest explicit owner instruction on ATIS operations supersedes conflicting older instructions, summaries, templates and assistant recommendations, subject to platform/security requirements. Retain historical records as history, not active authority. Changes to this policy require explicit owner approval and protected review. This document does not itself authorize any repository edit, publication, merge, trading or financial operation.

## 2. Deactivated ECG
The Execution Control Guard (ECG) is incomplete and deactivated. Never activate, invoke, integrate, depend on or recommend ECG in an operational task. Existing ECG source is historical/incomplete, not an enabled control. Do not modify or remove it as part of this governance change.

## 3. No fixed correction ceiling
The historical two-failed-attempt ceiling is abolished. No fixed retry or correction-cycle count applies. Within the exact authorized scope, one Codex agent may continue evidence-driven diagnose–correct–validate work while meaningful progress is possible. Stop for genuine blockers, missing authority, security risks, scope expansion, conflicting work, baseline drift or repeated ineffective actions without new evidence.

## 4. Minimal preparation
Before engineering, verify current repository identity, worktree, relevant owner authorization, active equivalent work and actual affected downstream consumers (tests, locks, trust profiles, historical integrity records and publication dependencies). Reuse verified evidence unless relevant state changed. Do not conduct broad audits or introduce extra approval gates without demonstrated need.

## 5. Authorization continuity
Carry forward valid owner authorization for its exact operation and scope across sessions and resumptions. Do not request duplicate conversational approval. New file scope, trust activation, protected publication and merges require the relevant separate authorization. Normal application permission prompts still apply.

## 6. Execution and evidence
Exactly one Codex agent; no subagents, delegation or concurrent equivalent task workers. Preserve accepted work and immutable historical evidence. Distinguish reported evidence, independently verified facts and unverified hypotheses. Use focused checks while correcting, then the required full final-candidate validation. A component PASS is not end-to-end acceptance.

## 7. Secure execution and publication
Keep ordinary engineering sandboxed. For authenticated GitHub operations on the owner's Windows host, use narrowly approved per-command execution under the correct Windows identity; verify GitHub identity and repository permissions without exposing credentials. Do not weaken TLS, keyring, CI, branch protection or risk controls. Preserve separate owner merge decisions. No trading authority is implied.

## 8. Assistant handoff discipline
Before issuing a command, check this policy against the latest owner instruction and the known task evidence. Provide one smallest useful next action, exact scope, authorization, expected evidence and stop conditions. Never silently reintroduce a superseded rule or repeat a completed investigation without a concrete evidence gap.

## 9. Proportional implementation
Prefer existing workflows and instructions. Do not add a new Smoothflow version, governance stage, mandatory runtime checker, ECG dependency or universal file-hash gate merely to enforce this document. Measure avoidable preflight stops, duplicate authorizations and obsolete-rule violations before proposing more automation.

## 10. Non-authority and adoption
This is an owner-governance proposal until accepted through the protected repository process. It is not a replacement for the existing security controls or authorization gates. It does not alter the current S4-07 candidate, historical recovery packet, trusted successor or PR #101.
