1. Accepted Baseline and Implementation Boundary
1.1 Baseline acceptance
Implementation begins from the accepted design and audit baseline. Earlier audit work is not restarted, repeated, renumbered or treated as incomplete solely because all verbatim historical text is not immediately available. R41-CI001-R41-CI113 form the mandatory cross-cutting invariant layer and supplement all surviving earlier audit invariants, including R39-I353-R39-I388.
1.2 In scope
Engineering contracts, Python package boundaries and dependency rules.
Canonical domain and event models, state machines and persistence ownership.
Market data, time/calendar, corporate actions and point-in-time research controls.
Strategy-proposal, economics, portfolio, risk, capital, OMS, broker, ledger and reconciliation components.
Runtime, recovery, security, observability, audit evidence, deployment and lifecycle gates.
Concurrent test design: unit, property, component, integration, failure, recovery, idempotency, race and acceptance tests.
1.3 Explicitly out of scope for this baseline
Real-money broker credentials, live submissions or any live-capital transaction.
Final broker selection or production account configuration. IBKR remains a leading candidate, not a binding implementation dependency.
A claim of profitability, legal/regulatory clearance, broker certification or production readiness.
Premature expansion beyond the initial liquid US equities and ETF universe or into high-frequency trading.
Strategy sophistication before the platform safety, accounting and evidence chain is verified.

4. Implementation Architecture
The default is a modular monolith with strict package boundaries and an in-process durable event workflow for early stages. This reduces distributed-systems failure modes while preserving contracts that permit later service extraction. No package may call a broker SDK except the broker adapter; no strategy may call OMS or broker directly.

Validated point-in-time market/reference snapshot and trustworthy clock.
Verified strategy/model/feature/config/release identity; fresh proposal.
Economic evaluation with expected net edge, costs, liquidity, capacity and uncertainty.
Current portfolio construction using positions, pending orders, unresolved effects and opportunity cost.
Atomic capital/risk reservation and independent risk/compliance/operational approval.

Fill → position/lot → ledger → broker/account reconciliation.

8.1 Transaction boundaries
A business state change and its outgoing event are committed atomically through the transactional outbox.
A consumed event is recorded with its handler/version before an economic consequence can be committed.
Ledger transaction and postings are atomic and balanced; an imbalance is rejected, never temporarily accepted.
Broker network calls cannot share a database transaction; the OMS records a durable submission attempt before calling and records result/ambiguity afterward.
Reservation release requires authoritative lifecycle/reconciliation evidence and an optimistic-concurrency check.

10. Definition of Done

10.1 Promotion rule
Passing a component DoD does not authorize the next lifecycle stage. Stage promotion requires the applicable GATE-S<n>-<nn> evidence set, independent approver separation where required, current external assumptions, and explicit authorization. Evidence invalidated by material code, configuration, model, broker, data, market, regulatory or infrastructure change cannot be reused silently.

18. Controlled Corrections and Baseline Closure Conditions
18.1 Stage 0 split
Stage 0A (baseline architecture and implementation framework) is established. Stage 0B (complete audit/invariant-to-implementation traceability) remains pending until the full Master Invariant Register is imported and a machine-readable coverage report demonstrates zero orphan mandatory invariants. Repository and CI bootstrap may proceed, but Stage 1 may not be formally completed or promoted while Stage 0B is open.
18.2 Traceability closure
Every mandatory canonical invariant must map to one or more atomic implementation requirements, an owning component/module, affected contract/schema/state machine where applicable, positive and negative/failure-path tests, monitoring/control, objective evidence and lifecycle gate. A reviewed NOT_APPLICABLE disposition is permitted only with attributable rationale. Missing historical wording must not be fabricated.
18.3 Provenance status
Every traceability record must carry provenance_status = CONFIRMED, RECONSTRUCTED, INFERRED or UNRESOLVED. Engineering inference must never silently acquire canonical/audit status.
18.4 Security lifecycle
Security is cross-cutting from Stage 1 onward. Stage 9 is the integrated hardening, adversarial validation and operational-readiness stage; it is not the first point at which security controls are implemented.
18.5 Broker capability boundary
Through Stage 10, broker work is limited to canonical ports, deterministic simulators, mocks, fault-injection adapters and conformance fixtures. A network-capable production broker adapter, production credential path or live submission capability is prohibited unless a later explicit lifecycle authorization permits it.
18.6 Delivery versus accounting semantics
Message/event delivery may be at-least-once. Authoritative financial effects must be effectively-once through durable identity, deduplication, idempotent application, fencing and reconciliation. No infrastructure component may be assumed to provide magical end-to-end exactly-once delivery.
18.7 Reservation expiry
Expiry of reservation authority does not prove that unresolved external liability disappeared. Unresolved order/broker effects retain conservative capital/risk holds until authoritative lifecycle/reconciliation evidence permits release.
18.8 Broker observation freshness
Broker evidence is authoritative for external reality as observed, but is never timeless. Every authorization-relevant broker/account observation must carry source, observation time, freshness/quality state and applicable authority epoch; stale, conflicting or unverifiable observations cannot satisfy a current exposure-increase gate.
18.9 Atomic requirement rule
IMP requirements used for implementation acceptance must be atomic. If only part of a requirement belongs to a milestone, decompose it into stable child requirements rather than marking an undefined 'portion' complete.
18.10 Gate completeness
Every build stage must have an explicit evidence gate or an explicitly documented non-promotional completion gate. Passing a stage gate never by itself grants paper, canary, production or live-capital authority.
18.11 Corrected baseline decision
Implementation Specification v1.0 Corrected - Final is internally verified as the controlled engineering baseline, with final implementation-baseline freeze pending Stage 0B traceability closure. No Master Audit restart or Phase 42 is required by these corrections. The architecture remains accepted; the remaining mandatory pre-freeze action is Stage 0B traceability closure against the complete Master Invariant Register. LIVE TRADING, CANARY, PAPER AND SHADOW EXECUTION REMAIN UNAUTHORIZED unless separately promoted through their defined evidence and authorization gates.
