## Boundary decision

This is audit tooling, not a domain runtime or authorization component. The
existing audit package owns validation and deterministic JSON export. The
checked-in JSON skeleton is an evidence artifact, not operational filesystem
state. The exporter returns text and performs no I/O. It needs no database,
persistence service, broker, execution, OMS, Risk, Compliance, scheduler, event
transport, external dependency, operator authorization, authorization persistence
or mode-transition orchestration. M1.5-M1.7 contracts remain unchanged.

The baseline entering this slice is M1.7 commit
`d72f45339a78125621ca48b4f15a9811fde81920`, with 357 passing tests. The skeleton
binds that baseline, not a future M1.8 commit or any uncommitted changes.

## Local engineering decomposition

The JSON schema and APIs are scoped engineering choices, not verbatim source
schemas. IMP-033-M1.8-01: validate required record structure and known schema,
status and provenance values before export. IMP-033-M1.8-02: export stable JSON
without changing caller data. IMP-001-M1.8-01: reject mismatched declared source
and baseline identities. These identifiers do not replace the programme register
or claim completion of the parent IMP requirements.

`manifest_skeleton` creates fresh planning data with no records and authorization
fixed to NONE. `validate_manifest` enforces section 3.1 fields, positive/negative/
failure test-reference categories, explicit provenance and duplicate-ID rejection.
`required_ids` is an explicit caller-selected coverage set; an empty skeleton
fails if required records are requested. Dependencies may reference external
requirements and are preserved without a claim that they are resolved.
`export_manifest` validates before serializing and sorts record identities and
object keys for deterministic output. Lists of evidence/test references preserve
the caller's declared order. Unknown fields are rejected rather than discarded.

## Usage

```python
from automated_trading_bot.audit.evidence import export_manifest, validate_manifest

# data is a decoded manifest; trusted_revision and trusted_source come from
# an independently established baseline, not from the untrusted data itself.
validate_manifest(data, expected_revision=trusted_revision,
                  expected_source_sha256=trusted_source,
                  required_ids=("IMP-033-M1.8-01",))
text = export_manifest(data, expected_revision=trusted_revision,
                       expected_source_sha256=trusted_source,
                       required_ids=("IMP-033-M1.8-01",))
```

The checked-in `M1.8-manifest-skeleton.json` is machine-validated by an acceptance
test. The empty records list deliberately avoids inventing historical coverage.
Populate records with the exact required fields and attributable references;
export does not upgrade status or provenance.

## Limits and deferred concerns

Validation is structural, not certification of evidence contents. Accepted or
Verified statuses are source declarations; this tool does not execute tests,
verify referenced files, authenticate approvers, certify expiry, validate dirty
worktrees, or establish complete historical invariant coverage. Callers must
supply trusted expected bindings and an explicit coverage set. Actual evidence
hash verification, lifecycle gate evaluation, evidence invalidation graphs,
signatures, storage and retention are deferred production concerns. A valid
manifest never implies operational permission or complete M1 programme exit.

Tests cover valid export, skeleton validation, ordering, nonmutation, incomplete
coverage, malformed structure, unknown enums/fields, duplicate IDs, stale binding
and invalid authorization declarations. Existing domain regression suites remain
part of the gate. No M1.9 or later milestone is started.
